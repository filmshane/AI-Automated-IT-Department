## 1. What this system does

For each **enabled** patch job on its patch day:

| Local time | Action | Script |
|------------|--------|--------|
| **08:00** | Day-of notice email (host list + patch time) | `patch_schedule_runner.sh morning` |
| **17:00** | Same-day reminder email | `patch_schedule_runner.sh reminder` |
| **patch_time** (e.g. 19:00) | Run `patch_and_verify.yml -e target_group=<GROUP>` | `patch_schedule_runner.sh run` |

Multiple groups can share a calendar day; each gets its own emails and run at its own `patch_time`.

Emails are built from the **live inventory group membership** (not a static host list).

```
    ├── HOWTO-patch-scheduler.md  # THIS document (canonical)
    ├── README-patch-scheduler.md # Short pointer
    ├── patch_calendar.yaml       # ★ SOURCE OF TRUTH — edit this
    ├── patch_calendar_lib.py     # Date math + inventory helpers (rarely edit)
    ├── patch_materialize_month.py# Expands calendar → concrete dates
    ├── patch_notify.py           # Builds/sends email via SMTP
    ├── patch_run.sh              # Wraps ansible-playbook
    ├── patch_schedule_runner.sh  # Cron entrypoint (morning|reminder|run)
    ├── schedule/
    │   └── active_jobs.conf      # ★ GENERATED — do not hand-edit
    └── generated/

        └── YYYY-MM-jobs/*.job    # One JSON file per job (debug)
```

### Edit vs generated

| File | Edit by hand? | Purpose |
|------|---------------|---------|
| **`patch_calendar.yaml`** | **YES — primary config** | Mode, contacts, app rules, one-off overrides |
| `patch_*` engine scripts | Only for behavior changes | Engine |
| `schedule/active_jobs.conf` | **NO** | Regenerated by materializer |
| `generated/*` | **NO** | Debug / audit snapshots |
| `logs/schedule_state/*.done` | Delete to re-fire a step | Idempotency markers |
| ansible user `crontab` | Rarely | Generic schedule (already set) |

## 4. `patch_calendar.yaml` — fields to modify

```yaml
  allow_job_ids:
    - ebstest_process_test      # only these job ids active while testing
  notify_only: false            # true = email only, no patching
```

### 4.2 Mail / SMTP

```yaml
mail:
  smtp_host: mail.jackinthebox.com
  smtp_port: 25
  from: ansible@corp.jitb.net
  always_cc: []                 # optional global CC list
```

### 4.3 Contacts (aliases used in `recipients:`)

```yaml
contacts:
  shane: shane.miller@jackinthebox.com
  manoj: manoj.sanap@jackinthebox.com
  l2: l2.run.operations@jackinthebox.com
  # add new people here, then reference by alias
```

**To change someone’s email:** edit the alias under `contacts:` (and any raw addresses under `overrides:`), then rematerialize.

### 4.4 Recurring applications (prod / test)

```yaml
applications:
  - id: ebs_test                 # unique job id (stable)
    name: EBS Test               # human label in email subject
    inventory_group: EBSTEST     # MUST match /etc/ansible/hosts group name
    tier: test                   # prod | test (documentation)
    week: last                   # first = 1st week of month; last = last week
    weekday: thu                 # mon tue wed thu fri sat sun
    patch_time: "06:00"          # 24h local PT — when playbook runs
    window: "06:00 AM - 08:00 AM" # text only (shown in email)
    recipients: [dba_oracle, shane, manoj]  # aliases and/or full emails
    owners_text: "..."           # free text for email body
    enabled: true                # false = never scheduled
    notes: "optional"
```

**Date rules:**
- `week: first` + `weekday: mon` → **first Monday of the month**
- `week: last` + `weekday: thu` → **last Thursday of the month**

```bash
# Morning notices for whatever is enabled + dated today

# Reminders
/etc/ansible/playbook/scripts/patch_schedule_runner.sh reminder
```

## 9. Common change recipes

### A. Change EBSTEST test recipients / Manoj’s address

1. Edit `contacts.manoj` and/or `overrides` recipients in `patch_calendar.yaml`
2. Rematerialize
3. Confirm with `grep EBSTEST .../active_jobs.conf`

### B. Move the process-test date/time

1. Edit override `patch_date` / `patch_time`
2. Rematerialize
3. Confirm enabled line

### C. Add a new application to the monthly calendar

1. Copy an `applications:` block
2. Set unique `id`, `inventory_group`, `week`, `weekday`, `patch_time`, `recipients`
3. `enabled: true`
4. While still testing, either keep `mode.testing: true` (new app stays inert) **or** add its `id` to `allow_job_ids`
5. Rematerialize

### D. Enable Clarity/WCTR after time is confirmed

1. Set `patch_time` and `window`
2. Set `enabled: true`
3. Add owner emails under `contacts` + `recipients`
4. Rematerialize
5. **Still testing?** Add job `id` to `allow_job_ids` only if you want it live early; otherwise wait for `testing: false`

### E. Go live for all groups

1. Confirm inventory groups and recipients
2. Set `mode.testing: false`
3. Disable/remove temporary overrides
4. Rematerialize and review `grep '|yes|'`
5. Watch logs on first real patch day

### F. Emergency stop

```bash
# In patch_calendar.yaml:
#   mode.testing: true
#   mode.allow_job_ids: []
python3 /etc/ansible/playbook/scripts/patch_materialize_month.py --also-next

# Or comment out crontab temporarily
crontab -e
```

## 12. `patch_and_verify.yml` behavior (summary)

- Requires: `-e target_group=<GROUP>`
- Validates group exists and has hosts
- Ensures `/opt/patches` on control node (ansible-owned)
- Per host: check-update → apply updates (kernel excluded) → compare yum/apt logs → zip → fetch to `/opt/patches/`

## 15. Zabbix maintenance mode (pre-patch)

**No prior playbook existed** for this — added as part of the patch scheduler.

| Item | Value |
|------|--------|
| Zabbix server | `smczabbixp01p.corp.jitb.net` (API https, Zabbix 6.2.x) |
| API user | `millershuxadmin` |
| Credentials file | `/etc/ansible/playbook/scripts/zabbix_api.env` (chmod 600) |
| Playbook | `/etc/ansible/playbook/zabbix_maintenance.yml` |
| Wrapper | `/etc/ansible/playbook/scripts/patch_zabbix_maint.sh` |
| Start | **10 minutes before** patch_time (`zabbix_maint` cron) |
| End | **10 minutes after** patch run finishes (then window is deleted) |
| Safety duration | **360 minutes** ceiling if remove step is delayed |
| Cron (start) | `*/5 5-23 * * *` → `patch_schedule_runner.sh zabbix_maint` |
| Remove | Handled inside `run` action after patch + 10m sleep |

### One-time setup (required before first use)

```bash
vi /etc/ansible/playbook/scripts/zabbix_api.env
# set:
#   ZABBIX_USERNAME=millershuxadmin
#   ZABBIX_PASSWORD=<your Zabbix UI password>
chmod 600 /etc/ansible/playbook/scripts/zabbix_api.env
```


### Lifecycle (per patch job)

```
T-10 min  →  Create Zabbix maintenance (all group hosts)
T+0       →  Start patch_and_verify.yml
T+done    →  Patch playbook finishes
T+done+10 →  Remove Zabbix maintenance window
```

Environment overrides:
- `ZABBIX_MAINT_MINUTES` — safety window length when creating (default 360)
- `ZABBIX_POST_PATCH_WAIT_SEC` — wait after patch before remove (default 600 = 10 min)

### Manual test

```bash
# Create maintenance for EBSTEST hosts now (uses inventory hostnames)
/etc/ansible/playbook/scripts/patch_zabbix_maint.sh present EBSTEST ebstest_process_test 2026-07-23 19:00 60

# Remove it
/etc/ansible/playbook/scripts/patch_zabbix_maint.sh absent EBSTEST ebstest_process_test 2026-07-23 19:00
```

### Scheduler behavior (testing mode)

For the EBSTEST process test at **19:00**, Zabbix maintenance is created around **18:50**.
Maintenance name pattern: `Linux-Patch-<job_id>-<date>`.

If Zabbix host **visible names** differ from inventory FQDNs, set hosts in Zabbix to match
or adjust `visible_name` / host list mapping in the playbook.
